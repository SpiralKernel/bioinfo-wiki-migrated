# 算法输入输出复杂度与数据结构

> 更新：2026-10-26；状态：可用；验证范围：2026-10-26核对原始与官方资料；本页Python微型计算已执行；人工数据不代表专业软件或真实研究性能。

算法是把明确输入转成所需输出的一套计算规则。例如“从100万个变异坐标中找出落在某区间的位点”，至少有三种解法：逐个扫描、排序后二分定位、建立区间索引。读完本页，你应能先写出任务，再判断计算是否正确、是否装得进内存，而不是只凭软件运行时间选方法。

前置只需列表、循环与文件的概念。后续学习[排序查找与哈希在生信中的应用](https://github.com/SpiralKernel/bioinfo-wiki/wiki/%E6%8E%92%E5%BA%8F%E6%9F%A5%E6%89%BE%E4%B8%8E%E5%93%88%E5%B8%8C%E5%9C%A8%E7%94%9F%E4%BF%A1%E4%B8%AD%E7%9A%84%E5%BA%94%E7%94%A8)、[图与最短路径的生信入门](https://github.com/SpiralKernel/bioinfo-wiki/wiki/%E5%9B%BE%E4%B8%8E%E6%9C%80%E7%9F%AD%E8%B7%AF%E5%BE%84%E7%9A%84%E7%94%9F%E4%BF%A1%E5%85%A5%E9%97%A8)和[动态规划与序列比对基础](https://github.com/SpiralKernel/bioinfo-wiki/wiki/%E5%8A%A8%E6%80%81%E8%A7%84%E5%88%92%E4%B8%8E%E5%BA%8F%E5%88%97%E6%AF%94%E5%AF%B9%E5%9F%BA%E7%A1%80)。

## 把生物问题变成计算任务

先写四项：输入对象、目标、约束、验收例。比如输入是同一参考版本的1基整数坐标，输出是闭区间[3,8]内的所有记录；重复位置应保留，缺失和非法坐标需拒绝。这样`[1,3,3,8,10]`应输出`[3,3,8]`。如果目标改为“不同位置数”，输出应是2；两个问题不能用同一个验收条件。

| 常见对象 | 合适的表示 | 要先确认的含义 |
|---|---|---|
| 样本×变异 | 稠密/稀疏矩阵 | 行列方向、剂量编码、缺失 |
| 标识到注释 | 字典或索引表 | ID是否唯一、一对多如何保存 |
| 有序坐标 | 排序数组 | 参考版本、染色体分组、边界 |
| 转录本/组装连接 | 图的邻接表 | 方向、权重、多条边、环 |
| 待处理任务 | 队列或栈 | 先入先出还是后入先出 |

数据结构决定允许高效执行哪些操作。把全部记录放在字典中不能自动得到按坐标顺序的范围检索；把一对多注释写成一个字符串值又可能覆盖信息。

## 用增长速度理解复杂度

令n为记录数，m为另一组记录数。O(n)表示计算量随n线性增长的上界量级，不是精确耗时；忽略常数和低阶项是为了比较扩大数据后的趋势。常见顺序是O(1)、O(log n)、O(n)、O(n log n)、O(n²)。最坏、平均和摊还复杂度应分别说明。[MIT算法课程](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-fall-2011/)以问题建模、正确性与资源分析共同组织算法。

在一百万记录上做一次扫描约检查一百万次。先排序约需n log₂n量级的比较，之后一次二分定位只需约20次比较。只查一次时，排序成本可能不划算；查一万次时，索引的成本更容易摊薄。读文件、解压与网络也会影响总时间，不能把复杂度当计时器。

## 亲手计算内存与操作次数

> 本页例子在项目根目录的Python中运行；标准库例子无需安装包，含NumPy/SciPy的例子先按[R包Python包与可复现环境](https://github.com/SpiralKernel/bioinfo-wiki/wiki/R%E5%8C%85Python%E5%8C%85%E4%B8%8E%E5%8F%AF%E5%A4%8D%E7%8E%B0%E7%8E%AF%E5%A2%83)建立项目环境。Windows命令使用`python`，macOS/Linux可使用`python3`；代码块可复制进该环境的Python交互会话，或保存为项目根目录下的临时脚本再用该环境解释器运行；不要保存到examples目录或任意外部目录后假定项目导入路径仍相同。除特别说明外，只向屏幕输出，不写文件。

```python
n = 1_000_000
print('scan_checks', n)
print('binary_upper_steps', n.bit_length())
rows, columns, bytes_per_value = 10_000, 1_000_000, 8
size = rows * columns * bytes_per_value
print('dense_GB', size / 10**9)
print('dense_GiB', round(size / 2**30, 2))
small = [1, 3, 3, 8, 10]
print('closed_interval', [x for x in small if 3 <= x <= 8])
assert [x for x in small if 3 <= x <= 8] == [3, 3, 8]
```

检查点：20、80GB、约74.51GiB，以及`[3,3,8]`。这仅计算原始double矩阵；副本、临时矩阵、索引和对象开销还会增加峰值内存。这里没有真的分配80GB，也没有把bit_length当作所有二分代码的实测步骤数。

## 正确性先于速度

对空输入、只有一项、重复值、边界相等、无结果做小例子，再比较不同实现。一个“每条只保留第一条注释”的程序可能很快，但若任务要求所有转录本，它仍然错误。随机小输入与简单穷举算法交叉核对，往往比只跑一个大文件更容易暴露逻辑问题。

规模检查也要具体。两两距离矩阵占O(n²)存储，n扩大10倍，元素数扩大100倍。稀疏格式仅在大多数元素不存储且操作保持稀疏时省内存；中途转成稠密仍会爆内存。并行只可能缩短可并行部分，还可能复制每个进程的数据。

## 运行异常时先查什么

| 症状 | 优先检查 | 可行处理 |
|---|---|---|
| 小数据正常、大数据内存不足 | 维度、dtype、隐式副本、n²对象 | 分块、流式、稀疏或换算法 |
| 查找很慢 | 是否每次重读或重排文件 | 重用索引，测量建索引与查询两阶段 |
| 某些边界漏记录 | 闭区间/半开区间、重复值 | 建立边界验收例，统一坐标 |
| 并行后更慢 | I/O竞争、序列化、线程过量 | 测单线程基线，减少嵌套并行 |

## 自测与答案

**问：O(log n)查询一定比O(n)扫描快吗？** 答：不一定。索引建立、文件定位、数据规模和查询次数共同决定总成本。**问：把样本数和位点数都翻倍，矩阵内存怎样变？** 答：元素数变4倍；若还计算样本两两距离，该部分也变4倍。将这些判断写在分析计划里，比运行失败后再找更大机器更有效。
